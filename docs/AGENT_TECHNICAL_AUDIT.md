## 1. What the system is
A FastAPI service running a flower shop's sales assistant on **WhatsApp (Cloud API) and Telegram**, an **admin dashboard** (single-page vanilla JS) and an **owner assistant** (a second LLM agent the owners talk to). Customers chat; the agent searches the catalog, builds orders, collects the delivery form, and routes every decision to the owners. Payment is a manual bank transfer confirmed by the owners.

### Path of one customer message
1. `app.py` verifies the signature and calls `agent.inbound()` (`agent.py:1557`).
2. `inbound()`: flood check; receipts (image/document, or pasted transfer text while an order waits for payment) are handled **at once by code**; everything else goes to the `Debouncer`.
3. `Debouncer` waits `DEBOUNCE_SECONDS=3` after the last message and merges a customer's messages (per-customer lock).
4. `process_batch` → `_batch` (worker thread): photo rules, Whisper transcription, lead alert, **fast path** (`fast.answer`) or `run_agent()`.
5. `run_agent()` builds the system message, optionally runs a code **pre-search** (`flowers_lookup` before the model), then a LangGraph loop (`agent` ⇄ `tools`, recursion limit 14).
6. Guards: `ungrounded()` blocks TL amounts/links no tool returned (one forced retry, then block + alert), `PROMISE` forces an admin flag; then `reply()`.

```python
class Debouncer:
    def __init__(self, handler, delay=None, on_busy=None):
        self.h, self.delay, self.on_busy, self.buf, self.t, self.locks, self.active = handler, delay, on_busy, {}, {}, {}, 0

    async def add(self, key, item):
        self.buf.setdefault(key, []).append(item)
        if key in self.t:
            self.t[key].cancel()
        self.t[key] = asyncio.create_task(self._wait(key))

    async def _wait(self, key):
        await asyncio.sleep(self.delay if self.delay is not None else float(cfg("DEBOUNCE_SECONDS", "3")))
        items = self.buf.pop(key)
        self.t.pop(key, None)
        lock = self.locks.setdefault(key, asyncio.Lock())
        self.active += 1  # messages (one batch per customer) being answered or waiting for their turn
        try:
            if self.on_busy and self.active > int(cfg("BUSY_MESSAGES", "50")):  # more than 50 at the same moment: say "one moment" now, the answer follows
                await self.on_busy(key, items)
            async with lock:
                await self.h(key, items)
        finally:
            self.active -= 1
```

## 6. Business logic
**Statuses** (`core.py`): `pending` → `quote`/`quoted` (custom item awaiting the owner's price) → `awaiting_payment` → `payment_review` (receipt in) → `confirmed` (paid, final) → `completed` (shipped); `rejected`/`cancelled` = Lost. `OPEN=(pending,quote,quoted)`, `LOCKED=(awaiting_payment,payment_review,confirmed,completed)`.

**Flow (code + prompt):** items → form → delivery choice → customer confirms the whole order incl. delivery fee and total (`confirm_item_list`; signature covers items and delivery details) → owner confirms (`decide_order`) → invoice PDF + bank details (code-written; the LLM words only two lines) → receipt → automatic check (`receipt.py`: amount, receiving IBAN, date, own-document detection) → owner confirms payment (`owner_says_ok`: explicit yes required; complaints never confirm).

**Edits / cancellations:** before final payment confirmation an edit applies at once and re-quotes (`change_apply(requote=True)`, status back to `pending`) and a cancel just cancels (undo within 30 min); after payment the owner decides (`change_request` stored; approval sends a new invoice with a code-written "why the total changed"; an approved cancel books a loss and deducts the sale).

**Prices:** `prices.json` merged into the graph, refreshed nightly 02:00-05:00 and on demand; the model may only state amounts that appear in a tool result.
**Delivery:** `data/delivery.json` areas (minimum, departure, jet fee); one shipment = one fee; owner note when the time is outside 08:00-23:00.
**Identity:** ids are WhatsApp numbers or `tg:<id>`; `core.link()` joins ids that share any identifier (user tag, phone given in a form); `core.contacts()` is the address book derived from orders.
**Owner side:** alert cards, "latest alert" focus rule, late-order alert (paid, 1 h after delivery time), morning report (on-going + today's shipments), Z-report 23:00, progressive week/month PDFs, lead alert, payment undo, shipping plan, orders report.

## 7. Performance findings (evidence)
*Measured on this machine:*
| Item | Result |
|---|---|
| `make_tools()` first / repeat | 38 ms / 0.8 ms (schema cache works) |
| `find_flowers` (260 products, in memory) | 1.1 ms per call |
| `core.orders()` (whole CSV parsed per call) | 0 rows 0.03 ms · 200 rows 0.87 ms · 2,000 rows 11.96 ms · 10,000 rows 49.62 ms (file 1.4 MB) |
| `kget` / `kset` (SQLite) | 0.10 ms / 0.13 ms per call |

**Ranked findings**
1. **LLM latency dominates.** Model call median 2.7-3.5 s plus the fixed 3 s debounce gave a *recorded* customer-visible median about 5.1 s and p90 about 8.3 s (10 scripted customers, gpt-5.6-luna, reasoning none). Tool turns need 2-3 sequential model calls.
2. **Large fixed prompt:** about 11,930 tokens of prompt + tool schemas per call; the provider cache makes it cheap, and volatile context follows the fixed part by design. The prompt is one dense 56-line block with overlapping rules; one conflict: the Telegram context line always tells the model to ask for the phone, while `sender_known()` already knows it for returning customers.
3. **`orders.csv` is re-parsed on almost every helper call** (`core.orders()` is called throughout: `open_order`, `last_form`, `contacts`, alerts, guards). Under 1 ms at 200 orders, linear later (about 50 ms per call at 10,000), and every write rewrites the whole file under one in-process lock.
4. **Single process, shared files** (SQLite, CSV, JSON written by the web process and background threads; the sandbox is a second process): fine for one shop, not horizontally scalable.
5. **Worker threads** (`asyncio.to_thread(_batch)`): fine for the tested 10 customers; the 50-concurrent target depends on thread pool size and OpenAI rate limits (not load-tested here).
6. A reply failing `ungrounded` triggers one extra full model call.

## 8. Risks and gaps
* Some behaviour still depends on prompt compliance (the item-list confirmation, "never flag_admin" rules); the project's answer has been functional guards (`owner_says_ok`, routing inside `decide_order`, `guard()`, `cancel_now`, `ungrounded_why`).
* Chat history is stored forever; only the last 8,000 chars reach the model.
* WhatsApp username / hidden-number fields are read best-effort; the real webhook shape is unverified.
* Delivery hours conflict in the data (website 09:00-21:00 vs override 08:00-23:00).
* No load test, no live metrics store; latency figures come from scripted runs. No git history; backups are dated file copies.
